전처리 아이디어

1. CROP 규칙을 만든 이유

① 각 변 12~15% expand — "detector 오차 + 잘린 부위" 대비
YOLO의 bbox는 완벽하지 않음. 몇 픽셀만 안쪽으로 치우쳐도 귀 끝, 꼬리, 주둥이 끝이 잘림. 
잘리는 부위들이 핵심 판별 단서라 결과의 영향을 최소화 시키기 위해. 

e.g.
귀 모양 (스패니얼의 늘어진 귀 vs 스피츠의 선 귀)
꼬리 형태 (시바의 말린 꼬리 vs 리트리버의 깃털 꼬리)
주둥이 길이 (퍼그 vs 콜리)

Q. 왜 그 비율로 설정했나 
타이트하게 자르면 이 정보 누수, 반대로 (30%+) 늘리면 배경·옆 사람·다른 개가 들어와 embedding이 오염될 가능성이 있음. 
12~15%가 "부위 보존 vs 배경 오염"의 절충점, 리서치 돌려보니 관행(10~20%)의 중간값임.

② 이미지 경계 clamp — 단순 버그 방지
잘라봤더니 expand한 좌표가 이미지 밖으로 나가면(x1 < 0 등) crop 함수가 에러 발생 혹은 라이브러리마다 다르게 동작함. 

③ 긴 변 기준 square — "체형 왜곡" 방지
Encoder 입력은 정사각형(224×224 등)인데, 개의 bbox는 보통 직사각형임. 무지성으로 Resize 하면

닥스훈트(장신 단족)가 보통 체형처럼 보이고, 
그레이하운드(날씬)가 통통해 보임
그래서 resize 전에 짧은 변을 늘려서 정사각형을 먼저 만들고(비율 유지) 그다음 resize합니다.

e.g. 닥스훈트 bbox가 400*200인 경우 
1) 긴 변 = 400. 짧은 변(세로 200)을 400으로 "확장"
   → 개를 늘리는 게 아니라, crop 영역을 위아래로 100px씩 더 넓게 잡는 것
   → 400×400 crop (개 위아래로 배경이 더 들어옴)

2) 400×400 → 224×224 resize
   가로 0.56배, 세로 0.56배  ← 같은 배율! 개 비율 그대로

핵심: 댕댕이를 변형하는 게 아니라 윈도우를 정사각형으로 키우는 것입니다. 

[코드]
def standard_crop(image, bbox, expand=0.15, out_size=224):
    """bbox: (x1, y1, x2, y2) absolute pixel"""
    H, W = image.shape[:2]
    x1, y1, x2, y2 = bbox
    bw, bh = x2 - x1, y2 - y1

    # ① 각 변 12~15% expand
    x1 -= bw * expand; x2 += bw * expand
    y1 -= bh * expand; y2 += bh * expand

    # ③ 긴 변 기준 square: 짧은 쪽을 긴 쪽 길이에 맞춰 "창을 넓힘"
    bw, bh = x2 - x1, y2 - y1
    side = max(bw, bh)                  # 예: 400
    cx, cy = (x1 + x2) / 2, (y1 + y2) / 2
    x1, x2 = cx - side / 2, cx + side / 2   # 중심 고정, 좌우/상하 대칭 확장
    y1, y2 = cy - side / 2, cy + side / 2

    # ② 이미지 경계 clamp
    x1, y1 = max(0, int(x1)), max(0, int(y1))
    x2, y2 = min(W, int(x2)), min(H, int(y2))

    crop = image[y1:y2, x1:x2]

    # ④ 이제 crop이 (거의) 정사각형이므로 resize해도 비율 왜곡 없음
    return cv2.resize(crop, (out_size, out_size))
한 가지 엣지 케이스: 개가 이미지 가장자리에 붙어 있으면 clamp 때문에 정사각형이 못 되고 약간 직사각형이 남습니다. 이때는 (a) 그 상태로 resize하고 미세 왜곡 감수, 또는 (b) 부족한 쪽을 padding(회색/reflect)으로 채워 정사각형 유지 — 어느 쪽이든 한 가지로 정해서 prototype과 inference에 똑같이 쓰면 됩니다. 저라면 (b) padding을 추천해요, 왜곡이 0이라서.


④ 가장 신경 많이 쓴 부분 "Prototype 구축과 Inference에 동일 적용" — 이게 제일 중요한 이유 #embedding 이미지를 숫자 좌표로 바꾼거

모델이 비교하는 건 내 강아지 embedding vs prototype embedding 
그런데 prototype은 15% 여유 있는 crop으로 만들고, 내 강아지는 타이트한 crop으로 넣으면 — 같은 골든리트리버라도 두 embedding이 다른 위치에 찍힘. 모델 성능과 무관하게 유사도가 낮아짐. 이런 train/inference 전처리 불일치가 실전 CV 시스템에서 제일 흔하고 제일 찾기 어려운 버그임.


2. Dedup = 중복 이미지 제거 (deduplication)

여러 데이터셋을 합칠 때 **같은 사진이 몰래 두 번 들어오는 것**을 찾아내는 작업입니다.

## 왜 생기냐

Stanford Dogs, Tsinghua Dogs, Oxford 전부 **인터넷에서 수집된 사진**이에요. 유명한 골든리트리버 사진 한 장이 이 사이트 저 사이트에 퍼져 있으면:

```text
같은 사진이
Stanford에는  golden_1234.jpg  (원본)
Tsinghua에는  n126_0567.jpeg   (약간 리사이즈된 버전)
```

두 데이터셋을 합치는 순간, 우리 데이터에 같은 사진이 2장 존재하게 됩니다.

## 왜 위험하냐 — 과적합이슈. 중복 자체보다, 중복된 두 장이 **train과 test로 갈라지면 학습데이터와 시험데이터가 같아짐. 

```text
Train: golden_1234.jpg        ← 모델이 이 사진을 학습(암기)함
Test:  n126_0567.jpeg         ← 같은 사진이 시험 문제로 나옴
```

우리는 3개 소스를 합치니까 이 위험이 특히 큼 — 그래서 A 파트에서 시간 배분 1위(20~25%)로 잡은 겁니다.

## 어떻게 찾냐 — 3단계 (점점 어려운 중복을 잡음)

**1단계: MD5 — "완전히 같은 파일"**

파일의 바이트가 1비트라도 다르면 다른 값이 나오는 지문. 이미 manifest에 계산돼 있어요.

```text
잡는 것: 복사-붙여넣기 수준의 완전 동일 파일
못 잡는 것: 리사이즈, 재압축된 같은 사진 (바이트가 달라지므로)
```

**2단계: pHash — "보기에 같은 사진"**

이미지를 흑백 8×8로 뭉개서 만드는 64비트 지문. 리사이즈·압축·약간의 밝기 변화에도 거의 같은 값이 나옵니다.

```text
두 사진의 pHash가 8비트 이하로 다르면 → 같은 사진 후보
잡는 것: 리사이즈판, 워터마크 추가판, 재압축판
못 잡는 것: 같은 개를 다른 각도에서 찍은 사진
```

**3단계: embedding 유사도 — "사실상 같은 장면"**

우리가 이미 아는 그 embedding으로 cosine similarity를 재서 0.92~0.96 이상이면 후보로 올립니다.

```text
잡는 것: 같은 촬영 세션의 연속 컷 (개가 1초 뒤 고개만 돌린 사진)
주의: 여기부터는 "진짜 중복"과 "그냥 많이 닮은 다른 개"의 경계가 애매
     → threshold 근처 후보들은 육안으로 확인하고 수치 확정
```

## 찾은 다음엔 — 삭제가 아니라 "그룹핑"

중복을 발견해도 지우지 않고 **같은 그룹 ID**를 붙입니다:

```text
golden_1234.jpg   dedup_group = DG_0042
n126_0567.jpeg    dedup_group = DG_0042   ← 같은 그룹
```

그리고 split할 때 **그룹 단위로** 나눕니다 — DG_0042는 통째로 train 아니면 통째로 test. 이게 저번에 말한 "Stratified **Group** Split"의 Group이 바로 이거예요. 이러면 중복 쌍이 train/test에 갈라지는 게 원천적으로 불가능해집니다.
